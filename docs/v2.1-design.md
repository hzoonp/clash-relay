# v2.1 design

v2.1 is an evidence-driven usability and qualification-observability release. It is not another architecture rewrite. The v2.0 clean-slate boundaries remain the platform contract.

## Entry criteria

Implementation work starts only after the active v2.0.x line has no known code-contract failure in the canonical production lifecycle and the operational SLO ring contains enough real attempts to distinguish configuration defects from normal qualification rejection.

A failed live probe or Promotion Guard block is not by itself a release defect. A mismatch between public declarations, doctor/preflight, and the production application path is a defect and must be fixed on v2.0.x first.

## Workstream A: production-parity preflight

Make `clash-relay doctor` exercise the same declaration-resolution boundaries that production consumes, while remaining safe and side-effect free.

Required outcomes:

- Policy Model v2 fragment resolution used by production qualification is checked by doctor.
- Registered ServiceQualification probes are validated without contacting providers in public-only mode.
- Missing Secret diagnostics name only the required Secret keys and never expose values.
- Schema/configuration failures identify the declaration and field closely enough for a Fork user to fix them without reading Python source.
- Private connectivity checks remain opt-in and bounded.

## Workstream B: provider-neutral qualification diagnostics

Strengthen the generic ServiceQualification surface rather than adding provider branches to the core pipeline.

Required outcomes:

- aggregate per-service qualification status is available through one provider-neutral result shape;
- provider implementations may add safe aggregate diagnostics without exposing node identities, URLs, credentials, or raw response bodies;
- client-path hardening remains declarative and optional per service;
- adding a service implementation does not require a core qualification-pipeline edit;
- cache policy remains owned by each registered service implementation.

## Workstream C: SLO-driven scheduler tuning

Do not tune scheduler hysteresis, debounce, cache TTLs, or quality thresholds from intuition alone. Use the bounded private operational SLO history and production metrics to identify a measurable problem first.

Candidate analyses:

- qualification rejection rate by failure category;
- retry recovery rate;
- Promotion Guard block rate;
- lifecycle-duration distribution;
- candidate churn and unchanged-release rate;
- cache hit/reprobe balance.

Any tuning proposal must state the observed failure mode, the intended metric movement, the rollback condition, and the regression tests that freeze the safety boundary.

## Deferred candidates

The following are candidates only after the three required workstreams above have evidence:

- multi-factor node quality scoring instead of binary pass/fail;
- region-aware stability scoring;
- richer release/rollback operational summaries;
- additional ServiceQualification providers.

They are not v2.1 commitments merely because the architecture can support them.

## Frozen invariants

v2.1 must not relax these contracts:

- Public Config remains v2-only.
- `subscription_1` remains restricted to browsing and AI inventories.
- an explicit node multiplier strictly greater than `2.0` is rejected; exactly `2.0` remains eligible.
- public deterministic subscription ordering remains `ingest_order`; the removed public `priority` alias does not return.
- builder does not mutate topology after compilation.
- Python production stages do not restore Python-to-Python subprocess/stdout JSON orchestration.
- the main qualification pipeline remains provider-agnostic.
- production publication remains bound to an exact validated commit SHA.
- Promotion Guard remains fail-closed before publication.
- generated production config, subscription responses, node-level qualification data, private KV state, caches, metrics, and SLO state remain private.
- rollback requires a versioned previous-release pointer, exact immutable bytes/manifest, current policy audit, and the complete stable Mihomo matrix; no legacy fallback returns.

## Release shape

v2.1 should be delivered through small independently reviewable PRs. Production-parity preflight comes first, then provider-neutral diagnostics, then any SLO-backed scheduler change. A feature that cannot preserve the frozen invariants stays out of v2.1.
