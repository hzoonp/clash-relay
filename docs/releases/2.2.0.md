# clash-relay 2.2.0

`2.2.0` is the Architecture Convergence release for the v2 line. It closes the production lifecycle, runtime topology, release engineering, and live-governance work that accumulated after `2.1.0` without changing the public routing contract or weakening any production safety boundary.

## Production lifecycle convergence

- GitHub Actions retains one canonical production mutation entrypoint: `scripts/run_production_release.py`.
- Automatic `push` and `schedule` events are hard-latched to dry-run behavior. Only an explicit manual `workflow_dispatch` with `publish=true` may change production state.
- A full production-parity dry run on exact governed `main` proved the automatic path remains non-publishing before cutover.
- The controlled production cutover then completed successfully through the same canonical lifecycle, with qualification, Promotion Guard, the complete pinned stable Mihomo matrix, publication, production proof, release manifest, derived state, metrics, scheduler observation, and Operational SLO all completing without warnings.
- Post-commit derived state and observability remain lifecycle-owned and cannot create a second publication authority.

## RuntimeGraph topology authority

- RuntimeGraph is the topology source of truth for downstream reachability, traversal, cycle detection, validation, and auditing.
- Validator topology checks no longer maintain an independent graph traversal implementation.
- Runtime graph snapshots remain detached from caller mutation.
- Browsing runtime hardening is independent from optional ACL group generation and cannot be skipped merely because ACL group specifications are absent.

## Runtime-generation boundaries

- Runtime configuration rendering is isolated behind `RuntimeConfigRenderer`.
- Rule loading, rendering, external-target validation, RULE-SET binding, and final MATCH compilation are isolated behind `RuleCompiler`.
- The generator is decomposed along application/runtime responsibilities without reintroducing a second topology builder or post-generation mutation path.
- Internal deterministic source ordering uses `ingest_order` / `source_ingest_order`; removed priority semantics are not restored as compatibility aliases.

## Release engineering and governance

- Reusable validation is the release quality authority, and release creation consumes the exact validated commit SHA.
- Release metadata contracts keep package version, runtime version, versioned release notes, changelog indexing, and the `[Unreleased]` comparison base synchronized.
- Live `main` governance requires pull requests and strict successful contexts `Validate exact commit / Validated SHA` and `Verify finalized Routing V2 graph`.
- A docs-only governance acceptance change proved both required contexts are emitted even when routing-sensitive source files are not modified.
- The production cutover candidate remained on the governed exact SHA throughout validation and publication.

## Verified production cutover

The final production-parity dry run executed against governed `main` at commit `ccf00272b7415f26cec9675bd233744761c8be0d` and completed with publication disabled.

The operator then explicitly authorized the production cutover. Workflow run `34234057401` executed as manual `workflow_dispatch` with publication enabled on that same exact SHA. The exact-SHA validation gate, Python compatibility/quality gates, deterministic generation, Mihomo v1.19.29 and v1.19.30 real startup/provider integration, Promotion Guard, production release transaction, production proof, and release manifest all passed. The canonical lifecycle finished in the verified phase with no warnings.

The release transaction stages immutable versioned config and manifest values, verifies writes by exact byte read-back, updates the client-facing production value and versioned pointers through the same verified-write primitive, and compensates to the prior production bytes/pointers on a commit failure where recovery is possible.

## Unchanged safety boundaries

- `subscription_1` remains limited to browsing and AI inventories and is never eligible for `general` routing.
- Explicit node multipliers strictly greater than `2.0` remain rejected; exactly `2.0` remains eligible.
- Multiplier parsing does not treat unrelated tokens such as architecture labels as multipliers.
- AI routing continues to exclude HK according to the canonical Routing V2 policy contract.
- Source-to-scenario reachability remains fail-closed before and after qualification.
- Production publication remains gated by qualification, Promotion Guard, every pinned stable Mihomo core, and exact-SHA validation.
- Automatic repository pushes and scheduled refreshes cannot publish production state.
- Generated production configuration, subscription URLs and payloads, node-level state, scheduler/cache state, production metrics, Operational SLO state, and Cloudflare KV data remain private.
- GitHub Releases remain source-only and contain no generated production configuration assets.

## Upgrade and compatibility

`2.2.0` does not change the Public Config v2 schema, the six public FlClash scenario names, the fixed client-facing Cloudflare KV key, the immutable release-object format, current/previous pointer semantics, or the user-visible source-permission contract. Existing v2 users can upgrade without a configuration-format migration.
