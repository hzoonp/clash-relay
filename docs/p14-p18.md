# P14-P18 architecture stabilization

P14-P18 turn the production pipeline into a smaller set of explicit contracts without changing the canonical six-scenario routing policy.

## P14 - Canonical RuntimeGraph

`src/clash_relay/runtime_graph.py` is the shared, side-effect-free view of a generated Mihomo graph.

It normalizes:

- proxy groups and their `proxies` / `use` edges;
- inline providers and provider proxy names;
- controlled `dialer-proxy` edges;
- recursive reachability and cycle detection;
- immutable logical candidate stages through `CandidateArtifact`.

Routing V2 audits consume this model instead of maintaining a second group-index implementation. The generator remains deterministic and no runtime graph object is serialized into the public candidate.

## P15 - Declarative production contract

Production-specific names and fidelity constraints live under `routing.contract` in `policies.yaml`.

The contract owns:

- the six public scenario group names;
- media/messaging/download automatic group names;
- general manual region choices;
- hidden ACL4SSR compatibility selectors;
- disabled compatibility groups;
- AI service target/prefix names and region display names;
- contract-required AI exclusions;
- ACL4SSR classification binding targets and relative priority edges.

`policy_contract.py`, `routing_policy_v2.py`, and `routing_v2_audit.py` validate the declaration. Core Python no longer assumes that `HK`, `网页浏览`, or `人工智能` are universal production constants. Older forks without `routing.contract` receive the previous canonical defaults for compatibility.

## P16 - Unified qualification pipeline

Production now has one qualification owner:

```text
generated.yaml
  -> 01-generated.yaml
  -> 02-browsing-transport.yaml
  -> 03-ai.yaml
  -> config.yaml
```

`scripts/qualify_candidate.py` invokes the existing browsing/transport and AI executors on private copies. The original generated candidate is never modified in place by production workflow orchestration.

The existing `qualify_browsing.py` and `qualify_ai.py` remain compatibility executors. Their probe and fail-closed behavior is unchanged.

## P17 - Versioned release transaction and rollback

The client-facing Cloudflare KV key is unchanged, so existing FlClash/Mihomo subscription URLs continue to work.

Before activation, the publisher stores immutable release objects keyed by the SHA-256 of exact candidate bytes:

```text
<production>.release-v1.<sha256>.config
<production>.release-v1.<sha256>.manifest
<production>.current-release-v1
<production>.previous-release-v1
```

The legacy `<production>.previous-v1` value is maintained during migration.

Publication order is:

1. stage and read-back verify the immutable new release;
2. migrate the currently served bytes to an immutable release when necessary;
3. update and read-back verify the fixed client-facing production key;
4. commit previous/current release pointers;
5. if pointer commit fails after the production key changed, restore the previous exact production bytes and pointers when a previous release exists.

Cloudflare KV does not provide a multi-key transaction and the client still reads one fixed key, so this is a compensating transaction rather than an impossible claim of cross-key atomicity.

Rollback is release-aware. The manual rollback workflow:

1. resolves `previous-release-v1`, with legacy `previous-v1` fallback;
2. runs the **current repository** production and Routing V2 audits;
3. validates the candidate against every pinned stable Mihomo core;
4. activates it through the same versioned release transaction.

A historical config that is syntactically valid but violates current source-isolation policy therefore cannot be rolled back.

AI cache and scheduler history are derived state. They are persisted after the production release commits and are best effort; a failure there produces a warning but does not falsely report the already committed production release as failed. Later runs rebuild missing state by probing again.

## P18 - CI and workflow consolidation

`tools/mihomo-versions.json` is the stable/prerelease core source of truth.

- CI exports its stable matrix from the manifest.
- Production and rollback use `validate_mihomo_matrix.py` rather than hard-coded version calls.
- Qualification downloads the first pinned stable core without embedding its tag in workflow YAML.
- Prerelease observation uses the first pinned prerelease entry.
- Production proof reads the validation-matrix report.
- Routing V2 drift guard triggers on the whole `src/**`, `scripts/**`, `rules/**`, and schema/declaration surfaces that can affect the finalized graph.
- Unit CI records coverage for Python 3.11 and 3.12 while preserving the existing real-Mihomo integration gates.

## Preserved invariants

P14-P18 deliberately preserve these production rules:

- canonical six public scenario selectors;
- subscription source-use isolation;
- `subscription_1` browsing/AI restrictions and multiplier filtering;
- ACL4SSR Online fidelity and intentional extensions;
- client-owned DNS behavior and optional sniffing;
- Browsing HTTPS qualification;
- media/messaging UDP/QUIC transport qualification;
- per-service AI qualification;
- dual stable-Mihomo validation before publication;
- no credential-bearing GitHub Artifact, Release, or Gist path.
